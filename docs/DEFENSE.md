# Подготовка к защите Assignment 4

## Что показать

1. Запустить `./run.ps1 demo` или `bash run.sh demo`.
2. Объяснить, что `Main` создаёт только `OrderFacade` и объекты данных. В нём нет создания сервисов.
3. Открыть `OrderFacade.placeOrder`: расчёт суммы, резервирование, оплата, доставка, уведомление.
4. Показать заказ на 19 500 KZT: 1 BOOK и 2 USB. Остатки меняются с 5/10 на 4/8.
5. Показать отмену: доставка отменена, платёж возвращён, остатки восстановлены. Повторная отмена ничего не дублирует.
6. Показать отказ оплаты и ошибку доставки. После обоих сценариев остатки совпадают с начальными.
7. Запустить тесты: `./run.ps1 test`. Тест ошибки доставки дополнительно проверяет нулевую сумму списаний.
8. Открыть `docs/REPORT.pdf` и объяснить UML и примеры Clean Code.

## Вопросы и опорные ответы

**Зачем здесь Facade?** Клиенту нужна операция «оформить заказ», но она требует согласованной
работы четырёх сервисов. Фасад прячет порядок вызовов, связывание по UUID, обработку ошибок и откат.

**Что делает каждая подсистема?** `InventoryService` рассчитывает стоимость и резервирует товар;
`PaymentProcessor` хранит списания и выполняет возвраты; `ShippingService` проверяет доступность
доставки и хранит отправления; `NotificationService` формирует сообщения и сохраняет их в outbox.
Это симуляция с состоянием, поэтому результат можно проверить, а не только прочитать в консоли.

**Почему резерв до оплаты?** Сначала проверяем, что можно выполнить заказ. Если оплата отклонена,
резерв снимается. Если позже не удалось оформить доставку, возвращается и оплата.

**Почему откат идёт в обратном порядке?** Сначала убираем более поздние эффекты: доставка,
оплата, затем резерв. Каждая компенсация выполняется даже при ошибке предыдущей;
ошибки сохраняются в `getSuppressed()`, исходная причина — в `getCause()`.

**Почему сбой уведомления не отменяет заказ?** Заказ уже успешно оплачен и доставка оформлена.
Результат содержит `notificationDelivered=false`; клиент видит проблему уведомления отдельно.
Фоновая повторная отправка за рамками этой учебной реализации.

**Могут ли сервисы работать без фасада?** Да. У них публичные методы, нет ссылок на `OrderFacade`.
Тест `directSubsystemUse` вызывает их напрямую. Обычный клиент `Main` использует только фасад.

**Это Adapter или Mediator?** Adapter преобразует интерфейс под ожидаемый контракт. Здесь
создаётся удобная операция поверх нескольких подсистем — это Facade. Подсистемы не знают
координатора и не отправляют ему события, как могло бы быть при Mediator.

**Какие принципы Clean Code применены?** Понятные названия, единая ответственность, скрытие
деталей и неизменяемые данные, ранняя проверка входа и атомарный резерв, сохранение причин
ошибок, идемпотентные компенсирующие операции. В отчёте есть аннотированный код для каждого.

**Почему BigDecimal?** Для денежных сумм нужна точная десятичная арифметика; `double` может
давать двоичную погрешность. Цены создаются из строк. Есть отдельная проверка 0.10 × 3 + 0.20 = 0.50.

**Что упростили?** Все данные в памяти, приложение однопоточное. Нет реальных списаний,
API курьера, отправки email, сохранения после перезапуска и завершения доставки.
Для реального магазина понадобятся база, контроль конкурентного доступа и надёжное
восстановление незавершённых операций.
